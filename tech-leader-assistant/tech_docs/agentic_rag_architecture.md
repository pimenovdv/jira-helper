# Архитектура Agentic RAG и Deep Research

Документ описывает подходы и архитектуру для внедрения продвинутых методов Retrieval-Augmented Generation (RAG) в проекте Tech Leader Assistant, в частности концепции Agentic RAG и Deep Research.

## 1. Agentic RAG

Традиционный RAG ограничивается семантическим поиском по предварительно нарезанным кускам (чанкам) текста из базы данных (например, OpenSearch). Подход **Agentic RAG** расширяет эти возможности за счет предоставления языковой модели доступа к инструментам (Tools/Functions), позволяющим ей самостоятельно принимать решение о том, как и откуда извлекать данные для ответа на запрос.

В рамках проекта необходимо реализовать агентный RAG со следующим набором инструментов:

*   **API-поиск по Jira**: Инструмент для прямого JQL-запроса к Jira для получения актуальных статусов задач, списков спринтов и комментариев (без необходимости предварительного индексирования всего объема данных в OpenSearch).
*   **API-поиск по GitLab**: Инструмент для запросов к GitLab API. Позволяет получать актуальную информацию о MR (Merge Requests), коммитах, ветках и пайплайнах.
*   **Глобальный API-поиск по Confluence**: Инструмент для выполнения CQL (Confluence Query Language) запросов к пространству Confluence для поиска актуальных страниц, метаданных и структуры документов.
*   **Векторный поиск по чанкам (OpenSearch)**: Инструмент для выполнения семантического поиска по уже проиндексированным фрагментам технической документации.

### Принцип работы:
1.  Пользователь задает вопрос (например: "Какой статус у задачи TLA-123 и какие документы по ней есть?").
2.  Роутер (LLM) анализирует запрос и решает, какие инструменты вызвать.
3.  Модель вызывает инструмент "API-поиск по Jira" для получения статуса TLA-123.
4.  Затем модель вызывает "Векторный поиск" или "Глобальный поиск по Confluence" для поиска связанных документов.
5.  Полученные данные объединяются, и модель генерирует итоговый ответ.

*Стек технологий: LangGraph, Langchain (Tool Calling, Agents).*

## 2. Deep Research

Для сложных запросов, требующих глубокого анализа и сопоставления большого количества данных из разных систем, используется архитектура **Deep Research**. Это многоагентная система, способная выполнять длительные исследовательские задачи.

### Компоненты системы Deep Research:
*   **Agent-Planner (Планировщик)**: Принимает высокоуровневый запрос (например: "Проанализируй причины задержки релиза v1.2, собери все баги, связанные с MR, и подготовь отчет"). Планировщик разбивает задачу на дерево подзадач.
*   **Worker Agents (Исполнители)**: Узкоспециализированные агенты, выполняющие конкретные подзадачи (например: Агент-аналитик кода, Агент-аналитик Jira). Они используют инструменты Agentic RAG.
*   **Agent-Reviewer (Рецензент/Критик)**: Оценивает результаты выполнения подзадач Исполнителями. Если качество результата неудовлетворительное, возвращает подзадачу на доработку с комментариями.
*   **State Management (Управление состоянием)**: Хранение промежуточных результатов, контекста выполнения и графа задач.

### Процесс выполнения (Workflow):
1.  **Планирование**: Планировщик формирует план (список шагов/графов подзадач).
2.  **Делегирование**: Подзадачи отправляются профильным агентам-исполнителям.
3.  **Исполнение**: Агенты собирают данные (через API Jira, GitLab, OpenSearch).
4.  **Ревью (Цикл обратной связи)**: Рецензент проверяет собранные данные. Если нужно, инициирует дополнительные поисковые запросы.
5.  **Синтез**: Главный агент (или Планировщик) собирает все проверенные данные в единый комплексный ответ или документ.

*Стек технологий: LangGraph (StateGraph, Multi-Agent Collaboration), возможность работы в фоновом режиме (async execution).*
